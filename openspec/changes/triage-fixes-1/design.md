# Design: Triage fixes 1

See proposal.md. Three mechanical fixes and one probe; the decisions
are about how the corpus and goldens move with them.

## Context

- `ops/fontset.rs::start_data` reads the data, defines fonts and the
  FontSet, and returns; the corpus generator writes `… StartData <data>
  end`. The reference converter refuses that form and accepts the
  canonical one (oracle triage T1).
- `ops/types.rs::type_` interns the type name as a literal name;
  `ops/output.rs` writes null as `-null-` in `==`'s form.
- The CIDInit-form CID font files fail in the reference converter
  inside its own `StartData` regardless of the trailing `end` (T2).
- Goldens are byte-compared; the `.ir`/`.pdf` content of the FontSet
  files does not depend on the program text, so those goldens should
  come out byte-identical after regeneration — a useful check.

## Goals / Non-Goals

**Goals:** the three behaviours match the reference's description;
corpus and goldens move with them through the generator and the update
flags, never by hand; the CIDInit finding either closes or becomes a
precise record.

**Non-Goals:** other triage groups; changing `=`; touching the harness.

## Decisions

**D1. `StartData` pops one dictionary.** After defining the FontSet it
pops the top of the dictionary stack, which the canonical form
guarantees is the procedure set's dictionary; if the top is not that
dictionary (a job that arranged the stack differently), it still pops
once — the operator's contract is "ends the `begin`", and a
`dictstackunderflow` on an empty user stack surfaces the job's mistake
as the reference does. The same treatment applies to the CIDInit-form
`StartData` only if the probe (D3) shows the canonical CID font form
expects it; otherwise it is left alone and the difference recorded.

**D2. Corpus regeneration over hand edits.** The generator drops the
trailing `end`; the thirteen files are regenerated by the ignored
generator test and the drift check must pass; `--update-ir`/
`--update-pdf` re-pin only goldens whose bytes changed (expected: none
for these thirteen, since only program text changed — assert that in
the notes). Files printing `type ==` or `null ==` get their
`% expect-output:` lines updated by hand, since they are hand-written.

**D3. CIDInit probe in the private tier.** Under the corrected loader,
run the two files through the oracle harness and, if still failing,
craft minimal variants under the build directory (entries reordered,
`FontMatrix`/`FontBBox` presence, the `(Binary)` operand, dictionary
nesting around `StartData`) to find the smallest form the reference
accepts. If the cause is in our synthesised form, fix the generator; if
the reference requires a form the reference text does not, record an
expected divergence candidate; if it reveals a loader bug, fix it here
when small.

**D4. `type` and `==`.** `type_` pushes the interned name with the
executable attribute; `==` writes `Type::Null` as `null` in the
syntactic form (the `=` path already does). Both are one-line changes
with unit tests and corpus updates.

## Risks / Trade-offs

- [Goldens that embed `type` output change] → only `.ir`/`.pdf`
  goldens of pages are byte-compared, and type names reach no page; the
  expectation headers in `.ps` files are what change.
- [A job relying on the old `StartData` stack behaviour] → none exist;
  the canonical form is what fonts in the wild use.

## Implementation notes

All five tasks are built. What the code and the probe pinned down:

- **D1, FontSet `StartData`** (`ops/fontset.rs::font_set_data`): after
  the fonts and the FontSet are defined and the two operands popped, it
  pops one dictionary through the interpreter's `end` path, so the
  permanent dictionaries are protected and a bare user stack raises
  `dictstackunderflow` naming `StartData`, after the definitions have
  taken effect (test `start_data_ends_the_procedure_sets_dictionary` in
  `ps-vm/tests/cff.rs`). The corpus scenario is
  `corpus/unit/fonts/fontset-dictionary-stack.ps`, generated.
- **D2, regeneration**: `CffFont::font_set` drops the trailing `end`;
  the thirteen FontSet files were regenerated by the ignored generator
  test and each differs from its predecessor by exactly the removed
  `end` line. The drift check passes and `difftest run` reported no
  golden mismatch, so no `.ir`/`.pdf` golden changed bytes and neither
  update flag was run — the check the design asked for holds.
- **D3, the CIDInit probe** — cause found, on our side, in both the
  synthesised form and the loader. Under the corrected FontSet loader
  the two files still failed in the reference converter. Scratch
  variants of `cidfont-type1-charstrings.ps` under `target/scratch/`,
  one variable at a time, run through the reference interpreter alone:

  | variant (dictionary arrangement at `StartData`) | trailing `end` | result |
  |---|---|---|
  | dictionary on the operand stack only (`currentdict end`, our form) | yes | refused, inside its `StartData` |
  | dictionary on the operand stack only | no | refused, the same way |
  | dictionary current *and* on the operand stack (`currentdict`) | no | accepted; the operand is left in place |
  | dictionary current and on the operand stack | yes | refused: underflow at the `end` |
  | dictionary current only (nothing on the operand stack) | no | **accepted**, dictionary stack back to its base |
  | dictionary current only | yes | refused: underflow at the `end` |
  | dictionary current only, `(Hex)` with the decoded byte count | no | accepted |

  So the canonical CIDInit form is `… 20 dict begin … (Binary) n
  StartData <data>`: the operator takes the form string and the count
  only, reads the CIDFont dictionary as the *current* dictionary, and
  ends both that dictionary and the procedure set's — nothing remains
  on either stack. Our loader took `dict (Binary) n` with the dictionary
  as an operand and our generator wrote `currentdict end` before
  `StartData` and `end` after the data: a form of our own that no
  reference accepts. The accepted variant's printed output agreed with
  ours except the `resourcestatus` size (T9, −1 against 0). Entry
  presence and order, `FontMatrix`/`FontBBox`, `CIDSystemInfo`, the
  offset arithmetic, and the `%%BeginResource` framing never needed
  probing: the smallest accepted form differs from ours only in the
  dictionary arrangement.

  Fixed here, both being small: `ops/cidinit.rs::start_data` uses the
  current dictionary, pops its two operands, and ends two dictionaries;
  `CidType1Font::file` emits the canonical form. `composite-fonts`
  gained a delta requirement pinning the operand form and the two pops,
  with a dictionary-stack scenario (test
  `start_data_ends_the_font_and_procedure_set_dictionaries` in
  `ps-vm/tests/composite.rs`). The two CIDInit corpus files were
  regenerated (again only the `currentdict end` and `end` lines moved;
  goldens unchanged). This extends D1's conditional clause: the CID form
  needed the pops *and* the dictionary read from the dictionary stack.
- **D4**: `type_` pushes the interned name with the executable
  attribute; `==` writes `Type::Null` as `null`. Unit tests in
  `ops/types.rs` and `ops/output.rs`; the delta spec's scenario for
  `null =` was wrong — it claimed `=` prints `null`, but `=` uses the
  `cvs` text, which is `--nostringval--` for null, and the reference
  interpreter prints exactly that (probe: `null = null ==`). The
  scenario now reads `null` then `--nostringval--`, which is what ours
  already did; `=` is unchanged as D4 requires. Corpus: six files carry
  `type ==` expectations (the triage's "seven" counted
  `type-and-conversion.ps` twice, or a file since merged) and two carry
  `-null-` (`standard-files.ps`, named in the triage, never printed a
  null); their `% expect-output:` lines and prose were edited by hand.
  New scenarios: `corpus/unit/interp/type-executable-name.ps` and
  `null-syntactic-form.ps`.
- **Gates**: `cargo test --workspace` 685 passed, 0 failed, 2 ignored
  (from 681); clippy clean with `--all-targets`; `cargo fmt`;
  `difftest run` 141/141 (from 138: three new scenarios);
  `parse-survival` 141 files, 0 failed; `lint-strings` clean;
  `openspec validate triage-fixes-1` valid.
- **Private-tier oracle run**, profile `default`, whole corpus, `--json
  target/oracle/report.json`. Before (the triage run): 138 files, 103
  pass, 31 fail, 3 expected-divergence, 1 divergence-closed; output 83
  same, 54 differs, 1 unavailable. After: **141 files, 118 pass, 19
  fail, 3 expected-divergence, 1 divergence-closed; output 102 same, 38
  differs, 1 unavailable.** Every T1, T2, T3, and T4 file now passes on
  the document channel except three named below, and reads `same` on
  the output channel except:
  - `cidfont-fontset.ps`, `cidfont-type1-charstrings.ps`:
    `resourcestatus` size 0 against −1 (T9, unchanged).
  - `scanner/integer-overflow-real.ps`, `scanner/number-like-names.ps`,
    `vm/integer-overflow-promotes.ps`: the reference's wider integers
    (T9, unchanged); the `type` lines now agree.
  - `interp/type-and-conversion.ps`: `cvrs` of −1 in radix 16 is a
    `rangecheck` there (T9, unchanged; also its converter failure).
  - `composite-vertical-width.ps` — **new**, visible only now: through
    `Identity-V` at size 10 from (0, 100) the reference leaves the
    current point at (5, 100), the glyph's full horizontal advance and
    no vertical movement, where ours leaves (0, 90), the default
    vertical advance of one em downward that PLRM3 §5.11 gives a
    CIDFont without vertical metrics. The rasters agree within the
    limit. Candidate (b), to be probed on its own (with explicit
    vertical metrics and a `CIDFontType 2` descendant) before any
    registry entry; follow-up **`vertical-writing-probe`**.
  - `composite-mixed-lengths.ps`, `composite-partial-match.ps`,
    `cidfont-type1-fallback.ps` — **new** document-channel failures,
    `text differs` only (rasters agree): the reference's text extractor
    yields the shown code bytes for runs through a non-Unicode CMap
    (`Syn-H`) and the CID for the Type 3 fallback glyph, ours yields
    other bytes (no ToUnicode is derivable for either). Comparison noise
    for text without a Unicode mapping — candidate (c); the harness
    could skip the text comparison when neither side carries a
    ToUnicode, or the corpus files could declare it. Follow-up
    **`text-extraction-without-unicode`**.

  The 19 remaining failures are otherwise the triage's T6 (six
  page-less text files), T7 (three declared limitations plus
  `derived-fonts.ps`), T8 (two page-device files), T9's `cvrs`, T11
  (two error-tolerance files), T12, and `deep-recursion.ps`'s timeout —
  none touched by this change.
